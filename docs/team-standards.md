# 统一开发与协作规范

适用于 OOTD AI 的代码、文档、模型实验和真机验证。开始工作前先确认自己的[职责和首周交付](first-week.md)。

## 任务认领与交接

- 用 GitHub Issues 跟踪可公开的任务，每项任务指定一位负责人和一次检查时间。状态统一写为 `待办`、`进行中`、`待验收`、`已验收` 或 `卡住`。
- 每个工作日更新一次在做的任务。把可运行结果、代码版本或复现记录贴在同一任务下。个人资料和内部素材链接通过团队内部渠道交接。
- 卡住时先记录环境、操作和第一条有效报错，再找对应负责人。需要决定时说明有哪些选项、影响哪项验收。等待期间先做独立任务。
- 交接统一写清下面几项，C 用同样的信息复测。

```text
任务编号和负责人
当前状态和对应版本
可检查的结果或报错
运行或复现步骤
下一步、接收人和检查时间
```

## 分支、提交和合并

1. 从最新的 `main` 建自己的分支。分支名用小写英文和短横线，如 `feat/android-viewer`、`fix/garment-load`、`docs/capture-guide`。
2. 每次提交围绕一个改动。提交标题写明做了什么，如 `feat: load garment by ID`。提交前用 `git status --short` 和 `git diff --cached --name-only` 核对入库文件。
3. 推送自己的分支并向 `main` 提交 PR。描述写清对应任务、改动、运行或测试步骤、实际结果和已知问题。还没验证的项标记“待验证”。
4. 由另一位队员复核。C 跟进验收和复核状态，具备权限的同学在通过后合并。涉及资产格式、重建路线或功能范围的改动先与队长确认。日常改动走 PR。

## 代码和接口

- 代码按实际模块组织，Android 界面与模型实验各有独立的运行说明。沿用所用语言的默认格式。变量和函数命名说明用途，注释解释复杂逻辑和数据限制。
- 新增依赖要记录用途与版本。安装、编译和运行步骤写在对应目录的 README，配置示例只放占位值。改动时一并更新相关说明。
- 同一件衣物从素材清单、三维资产到推荐结果始终用同一个编号，如 `top-001`。人物用独立编号，如 `person-001`。资产交接写清编号、文件路径、格式和加载方式。
- 改动共享字段或资产格式前，由产出方和使用方先对齐，并在 PR 附一份无个人信息的输入输出示例。推荐结果至少给出衣物编号和理由，加载前确认编号存在并对应可用资产。

## 素材与实验结果

| 内容 | 位置 |
| --- | --- |
| 本人照片、视频与衣物原始采集 | `local-data/` |
| 下载的模型权重 | `weights/` |
| 导出的个人模型、实验日志和生成结果 | `outputs/` |
| 密钥及本机配置 | 本机环境变量或已忽略的 `.env`、`local.properties` |

仓库是公开的。可识别人物的影像、重建资产、凭据、内部链接及报名个人信息留在本地或团队内部。提交第三方代码或可分发素材时，记录名称、来源、版本、许可和团队改动。

## 资产交接的最小格式

A 与队长把文件和清单交给 B，C 使用同一份清单复测。清单保存在 `outputs/handoff/assets.csv`，每个资产一行。文件名用编号，后缀用实际导出格式。路径相对于 `outputs/handoff/`。资产来源填 `test` 或 `participant`，文件存在并经 B 确认可加载后才用于换装。

```csv
asset_type,asset_id,relative_file,source
person,person-001,person-001.glb,participant
garment,top-001,top-001.glb,participant
garment,top-002,top-002.glb,participant
```

以上是填写示例。参与者素材及派生模型随清单留在本地或团队内部，公开记录只写编号和结果。

## 验收和 AI 记录

- 先自己跑一遍，再交给另一位队员复测。记录版本、设备、输入编号、步骤、预期、实际和结论。对阻塞保留可复现的报错。真机、模拟器、测试资产和本人资产的结果分别登记。结论统一用「通过」「失败」「未测」。缺输入或设备时填「未测」，并写明缺什么。
- 使用 AI 辅助编程时记录日期、任务、提示词要点、采纳内容、人工修改、验证结果和对应提交。把个人信息和密钥留在工具输入之外。提交人应能解释代码如何运行以及如何验证。
